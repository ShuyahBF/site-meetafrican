Persistance à créer (MongoDB Atlas)
Base « vidal »

    

      
Base de données MongoDB Atlas dédiée : vidal. Aucune table à créer manuellement : les collections apparaissent automatiquement dès le premier document inséré par le backend. Le patient est une entité à part entière, distincte des contacts existants — mémorisé uniquement si le médecin clique sur « Enregistrer » ; sinon la consultation reste ponctuelle. Six collections dans vidal :

      
medecins — un document par médecin autorisé à utiliser VIDAL (facturation par médecin) : nom (MAJUSCULES), prenoms (1ère lettre en majuscule), email (minuscules, obligatoire et unique — identifiant de connexion du médecin), otp_email_actif (bool — envoi d'un code OTP par email à la connexion si activé), telephone, whatsapp (nullable — vide = identique au téléphone, résolu à la lecture, jamais figé en base), specialites[], cliniques[] (tous les établissements où il/elle intervient), numero_ordre, date_enrollement_vidal, etat (ACTIF|INACTIF|SUSPENDU), forfait_type (MENSUEL|USAGE), montant, volume_consomme, date_expiration, medecin_user_id. Configurable uniquement par l'admin — voir la fiche dédiée « Admin — Médecins VIDAL ». À la 1ère connexion en rôle médecin : recherche par email (identifiant fiable, plus le nom qui peut être ambigu), création auto si absent (forfait mensuel 25 000 FCFA, expiration à 30 jours) ; accès autorisé seulement si etat = ACTIF ET date_expiration non dépassée, sinon le menu « Analyse de prescription » est grisé (simulé ci-dessus via « Simuler licence expirée »).

      
api_calls — un document par appel réel au serveur VIDAL depuis cette fenêtre (recherche référentiel, calcul de clairance, sécurisation), qu'il y ait eu enregistrement du patient ou non : endpoint, medecin_id, client_id, patient_id (nullable), called_at, success, duration_ms. Alimente la carte « Statistiques d'utilisation VIDAL » (total, par médecin, par période) — utile aussi pour suivre la consommation par rapport au quota du contrat VIDAL.

      
patients — créée uniquement à l'enregistrement. Un document par patient : id (identifiant unique généré, seule référence utilisée partout ailleurs — ex. PAT-2026-00042), name, client_id, profil clinique de référence (date de naissance, sexe...), created_by (médecin créateur, seul à voir le nom par défaut), shared_with_colleagues (bool), created_at. C'est la SEULE collection où le nom du patient est stocké.

      
patient_access_requests — une demande de code par confrère non-créateur : patient_id, requested_by, creator_id, otp_code (4 chiffres, généré par le système), status (PENDING|VERIFIED|EXPIRED), created_at, expires_at. Le bouton « Demander le code » envoie un WhatsApp au créateur (réutilise le relais WA existant) ; le créateur transmet le code reçu au confrère de vive voix/WhatsApp ; la saisie correcte marque la demande VERIFIED et débloque le nom pour ce confrère sur ce patient.

      
patient_treatments — un traitement en cours par document, rattaché à patient_id uniquement (jamais au nom). Alimentée à chaque sécurisation d'un patient enregistré ; permet de préremplir automatiquement l'étape 2 à sa prochaine consultation.

      
securisation — un document à CHAQUE clic sur « Sécuriser », patient enregistré ou non (c'est ce qui donne son id unique à chaque analyse, ex. RX-2026-483920, affiché en badge sur le résultat) : lignes soumises, XML envoyé, réponse VIDAL brute (XML /alerts/full ET HTML /alerts/full/html — vidal_html_snapshot, le document affiché tel quel dans l'onglet « HTML VIDAL » ; on fige cette copie à l'instant T plutôt que de rappeler VIDAL plus tard, car son contenu peut évoluer avec les mises à jour du référentiel — important pour l'audit médico-légal), résumé des alertes, medecin_id, client_id, created_at, et patient_id si enregistré / null sinon. C'est exactement cette collection qu'affiche le bouton « Historique », et « Charger » recharge tout le formulaire depuis le document sélectionné.
      Champs de traçabilité pour le pictogramme rouge/bleu : status (ALERTED|CORRECTED|VALIDATED|CLEAN), origin_id (sécurisation initiale corrigée, null sinon), alerts_summary, status_history (jamais écrasé).
      Champs ajoutés pour « Imprimer Ordonnance » : ordonnance_pdf_ref (référence vers le PDF généré, stocké en GridFS ou object storage — jamais le binaire directement dans le document), ordonnance_generated_at, verification_expires_at (validité du QR, 90 jours par défaut). Le QR encode une URL /rx-verify/{id}?exp=...&sig=... dont la signature est un HMAC calculé UNIQUEMENT côté serveur avec une clé secrète — jamais stockée en base ni générée côté client (contrairement à la démo de cet aperçu).

      
Pour une consultation non enregistrée : patients et patient_treatments restent vides (aucun dossier durable créé), mais securisation enregistre quand même l'analyse (patient_id à null) — sans quoi l'URL de vérification imprimée sur l'ordonnance n'aurait rien à vérifier. api_calls comptabilise l'appel dans tous les cas, pour les statistiques.

      
Envoi WhatsApp de l'ordonnance — pas de nouvelle collection : réutilise whatsapp_messages, qui reste dans la base principale de Sawali (pas dans vidal, puisque c'est une infrastructure déjà partagée par tout le site), avec un document par envoi : related_analysis_id, to (numéro patient), message_type: "document", template_name, wa_status (SENT|DELIVERED|READ|FAILED), sent_at/delivered_at/read_at, wa_message_id (mis à jour au fil des webhooks Meta, comme pour les autres messages).
      

Un modèle WhatsApp Business pré-approuvé est obligatoire pour ce type d'envoi (document hors fenêtre de conversation de 24h) — à configurer dans Réglages admin > Modèles WhatsApp. Nom proposé : ordonnance_pdf_fr (catégorie UTILITY, en-tête type Document, corps en français : « Bonjour {{1}}, voici votre ordonnance du {{2}} établie par le Dr {{3}}. Merci de la présenter à votre pharmacie. », pied de page « Sawali Smart Systems — message automatique »).
